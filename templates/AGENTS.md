### Key Technologies

## HTML-first blocks (toolchain)

New blocks are **HTML-first**. You edit only the Block Source `blocks/{name}/{name}.html` (Tailwind classes + `data-*` markers) and, optionally, `blocks/{name}/{name}.enhance.js`. Everything else is a Generated Artifact and must never be hand-edited: `_{name}.json`, `{name}.js`, `{name}.css`, the `component-*.json` aggregates, the block entry in the `section` filter of `models/_section.json`, and the block markup inside `drafts/{name}.html`. Change the Block Source and rebuild instead.

### Commands

- `npm run aem:init` — idempotent Toolchain Bootstrap: re-applies aem-kit (npm scripts, configs, hooks, `AGENTS.md`, agent adapters) from `aem-kit.config.json`. Run it after changing the config or updating aem-kit
- `npm run aem:generate-block -- <name>` — Block Scaffold (Block Source with `heading` + `text` fields, formatted with Prettier, and a Draft, copy in the project language) then Block Build. Name is normalized to kebab-case without accents (`"Seção X"` → `secao-x`); aborts if the block or its Draft already exists
- `npm run aem:build` — Block Build for every Block Source + `build:json`. One block only: `npm run aem:build -- <name>`
- `npm run aem:up` — AEM CLI (`--html-folder drafts`) + `aem:watch`
- `npm run aem:watch` — rebuilds a block when `blocks/{name}/{name}.html` or `blocks/{name}/{name}.enhance.js` is created, changed or removed
- `npm run check` — full validation (what CI runs): Block Build of every block (fails if Generated Artifacts are not committed), ESLint, Stylelint, Prettier, html-validate, axe and Lighthouse on every Draft (all 4 categories)
- `npm run aem:lighthouse` — Lighthouse (mobile, like PageSpeed) on the Drafts: Performance, Accessibility, Best Practices and SEO must each score at least `lighthouse.minScore` (default 90) in `aem-kit.config.json`. One block: `npm run aem:lighthouse -- <name>`; a page: `-- --url <url>`; the deployed site of the current branch: `-- --deployed` (`https://{branch}--{repo}--{owner}.aem.live` for `main`, `.aem.page` otherwise, pages from `lighthouse.urls`). When the first Performance run is below the minimum it runs `lighthouse.runs` times (default 3) and keeps the median. On a failure it prints the audits that cost the most points
- Pre-commit (husky → `aem-kit check --staged`), on staged files only:
  1. Block Build of the blocks whose Block Source or `enhance.js` is staged (including deletions); stages only their Generated Artifacts (`_{name}.json`, `{name}.js`, `{name}.css`, `drafts/{name}.html`, `models/_section.json`, `component-*.json`)
  2. ESLint, Stylelint and `prettier --check` on the staged files
  3. Semantics: Source Gate + `html-validate` (`.htmlvalidate.json`) on those Block Sources
  4. Accessibility: axe (WCAG 2.1 A/AA) on `drafts/{name}.html` rendered in headless Chromium (Playwright). `serious`/`critical` violations block the commit; `moderate`/`minor` are warnings
  5. Lighthouse on those Drafts: Accessibility, Best Practices and SEO below the minimum block the commit. Performance is not measured here (too noisy on a dev machine): CI (`npm run check`) blocks it, and `.github/workflows/aem-kit-lighthouse.yaml` measures the real pages after every push to `main`, once AEM Code Sync has published the code. With `tracking` configured, that workflow blocks on the score **without GTM** (`--block '*googletagmanager.com*'`: the tags are managed in GTM, outside the repository) and then reports the score with GTM in the job summary (`--report`, never fails)
- Lighthouse rules: fix the cause, never lower `minScore`, add `skipAudits` or set `lighthouse: false` to make a check pass (only with the human's explicit approval). Drafts must load like a real page: keep `<header></header>` and `<footer></footer>` around `<main>` (without them `loadHeader` throws and Best Practices drops), and commit Draft images optimized (WebP, sized to their display; Performance measures them). SEO `is-crawlable` is skipped on `*.aem.page`/`*.aem.live` (AEM always sends `noindex` there) and `canonical` on Drafts
- Never bypass the hook with `--no-verify`: CI runs the same checks

### Block Source markers

- Root element: `data-block="{name}"` (must equal the folder name) and `data-title` (component name shown in Universal Editor; its kebab-case must equal `{name}`, so no accents: `toClassName` from `scripts/aem.js` keeps only `[0-9a-z]`; the scaffold strips them for you). Root classes are copied onto the block element
- Fields: `data-field="{field}"` + `data-component` (`text` default | `richtext` | `reference` | `select` | `link`) + `data-label` (label in UE; `aria-label` is also accepted). Field names must be unique across the whole block (block fields + item fields)
- `select`: `data-options="azul:Azul, branco:Branco"` (`value:Label`, the first is the default). It does not fill content: the runtime sets `data-{field}="{value}"` on the element, so style variants with `data-[{field}=azul]:bg-secondary`. It may sit on the `data-item` element itself (e.g. a card color) and contain other fields. Names must not end in `Type`, `Title`, `Text`, `Alt` or `MimeType` (AEM merges those into a sibling property). The Draft shows one item per option, so axe checks every variant
- `link`: only on an `<a>`; the model gets `{field}` (URL, `aem-content`) and `{field}Text` (label), delivered as one `<a>`; the runtime copies href, text and title into your `<a>` and keeps its classes. The `<a>` content is the default label
- The content inside a field element is its default value: it becomes the UE template value and the Draft content. `text` defaults have tags stripped; HTML comments inside a field are ignored (use them for sample copy that must not become content). Leave the element empty for a field that starts empty
- Repeatable items: `data-item="{item-id}"` + `data-item-title` on one element. Only the first `data-item` defines the model and it needs at least one field; fields outside it are block fields. Further `data-item` siblings (e.g. the 4 cards of a design) are Draft samples only: they show up in the Draft (and are checked by axe) but the runtime keeps just the first as template. The build seeds one item (`item_0`) in the UE template; authors add more with +. Child items are edited in the Universal Editor content tree (or by clicking them on the canvas), not in the block's properties panel
- Simple lists (one short text per entry): put `data-multi` on the repeating element itself, e.g. `<li data-field="itens" data-component="text" data-multi data-label="Itens">`. The field becomes a multi-value `text` field (`multi: true`) edited right in the block's properties panel, one input per entry; the runtime repeats that element once per value. On a field it works with `text` only, outside `data-item`. Needs `multi-field.enabled` in `xwalk.json` (`aem:init` ensures it)
- Lists whose entries have several fields (e.g. cards with color, image and text) and must be edited in the block's properties panel: add `data-multi` to the `data-item` element. The item becomes a composite multi-field (`container` + `multi: true`, named after `data-item`, labelled by `data-item-title`) instead of child items; AEM delivers its entries as `<ul><li>` (one element per entry) or separated by `<hr>`, and the runtime fills each copy of the item by type (pictures → `reference`, links → `link`, other blocks → `select`/`text`/`richtext` in order; a select only takes a value from its options, else its default); a `richtext` keeps all its paragraphs/lists, leaving one text block for each `text`/`richtext`/`select` field after it. Limits from AEM: only the first `richtext` of an entry is rendered; no default entries in the UE template (authors add them with Add). Prefer `data-multi` over child items whenever authors should edit the list in the panel
- Runtime (`scripts/render-template.js`): clones the template, fills fields in document order (`text` → text only; `richtext`/`reference` → authored nodes), skips items whose cells are all empty, then strips the authoring markers (`data-block`, `data-title`, `data-item`, `data-item-title`, `data-field`, `data-component`, `data-label`, `data-multi`, `data-options`). Any other `data-*` attribute (e.g. `data-faq-item`) is kept, use it as a hook for `enhance.js`
- Put `reference` fields on a container element, never directly on `<img>` (void elements cannot receive the authored `<picture>`)

### Tracking (Google Tag Manager + dataLayer)

- Configured by `tracking` in `aem-kit.config.json`: `gtmId` (default container), `defaults` (fields sent with every event, e.g. `marca`, `pageName`) and `pageview` (default `true`). `npm run aem:init` writes a managed region at the top of `head.html` (inline script, after the CSP meta) that creates `dataLayer`, pushes the `pageview` and loads GTM, and the Managed File `scripts/datalayer.js`. Never edit either by hand
- Per page (AEM page metadata): `gtm-id` replaces the container and `page-name` replaces `pageName`. GTM is skipped inside the Universal Editor (`*.adobeaemcloud.com`) and on localhost (add `?gtm=on` to test it there); the `dataLayer` events are pushed everywhere, Drafts included
- Clicks are declarative: add `data-track` to the clickable element in the Block Source (the runtime keeps it). It pushes `{ event: 'clique', eventLabel: pageName, eventAction: 'clique', eventCategory: 'interacao', pageName, locationElement: 'body', typeElement: 'button', textElement: slug(text or aria-label), …defaults }`. Override any of them with `data-track-label`, `-action`, `-category`, `-location`, `-type`, `-text`, or the event name with a value (`data-track="outro_evento"`). `data-track-when="expanded"` only tracks clicks that leave `aria-expanded="true"` (open an accordion item, not close it). Text from the author changes with it, so prefer the default `textElement`
- Other events (form submissions, video plays…): `import { track, slug } from '../../scripts/datalayer.js'` in `enhance.js` and call `track({ event, … })`; the defaults fill the rest. `slug('Entre R$500 mil')` → `entre_r$500_mil`
- Personal data (name, e-mail, phone) only when the analytics spec asks for it, and only from the form's own submit-success event
- Measure the cost of the tags: `npm run aem:lighthouse -- --deployed --block '*googletagmanager.com*'` scores the page without GTM; `npm run aem:lighthouse -- --deployed --report` scores it with GTM without failing. The post-deploy workflow runs both. A low score with GTM is for whoever manages the container (fewer or delayed tags); a low score without GTM is the site's code and must be fixed

### Behaviour (`{name}.enhance.js`)

- Optional and hand-written (ESLint/Airbnb applies). Signature: `export default function enhance(block)` (may be `async`); it is called after the template is rendered. See `blocks/faq/faq.enhance.js`

### Conventions

- Tailwind is required for **new** blocks. Legacy Blocks without `.html` (`cards`, `columns`, `hero`, `fragment`, `header`, `footer`) remain valid with hand-written CSS
- Responsive: mobile first with the Tailwind default breakpoints `sm` 640px, `md` 768px, `lg` 1024px, `xl` 1280px, `2xl` 1536px. Hand-written CSS uses the same widths in `min-width` queries
- Language: UE labels (`data-label`, `data-item-title`), default copy and Drafts are in {{LANGUAGE_NAME}}
- Design tokens: use the project theme (below) instead of arbitrary values such as `bg-[#004664]`. Add or rename tokens in `aem-kit.config.json` and run `npm run aem:init`
- Source Gate (fails the build; messages in PT-BR): `data-component` limited to `text` | `richtext` | `reference` | `select` | `link` (`link` only on `<a>`), `data-label` (or `aria-label`) on every field, at least one heading (`h1`–`h6`), `alt` on every `<img>`. The build also fails on: missing `data-block`, `data-block`/`data-title` not matching the folder, no fields, duplicate field names, `data-item` without id or fields
- Drafts: `drafts/{name}.html` is a full page; the block markup in it is resynced from the field defaults on every build (manual edits inside the block are overwritten, the rest of the page is kept). Preview at `/drafts/{name}` with `npm run aem:up`
- Global CSS: `styles/styles.css` only has a reset in `@layer base` (so Tailwind utilities win) and the font variables. There is no global typography, button, link or section layout styling: style everything inside the block
- Font: {{FONT_FAMILY}} is the main font (`--font-family`, used by `--body-font-family` and `--heading-font-family`; `font-sans` in Tailwind), with a metric-matched fallback in the aem-kit region of `styles/styles.css`. `styles/fonts.css` loads it after LCP. Both come from `font` in `aem-kit.config.json`
- Formatting: Prettier (+ `prettier-plugin-tailwindcss` class sorting) only covers Block Sources (`blocks/{name}/{name}.html`) and `styles/*.css` (see `.prettierignore`). JS is formatted by ESLint (`npm run lint:fix`) because Prettier conflicts with it
- `styles/tailwind.css` only feeds Tailwind IntelliSense in the editor; pages never load it
- Each block's compiled CSS is wrapped in `@scope (:has(> .{name}))` (the block and everything inside it): its utilities only apply inside that block, so several blocks on one page never override each other's classes (e.g. one block's `flex-col` beating another's `xl:flex-row`). Elements you create in `enhance.js` must live inside the block to get its classes
- See `CONTEXT.md` and `docs/adr/0001-html-first-blocks-tailwind.md`

## Code Style Guidelines

### JavaScript
- Use ES6+ features (arrow functions, destructuring, etc.)
- Follow Airbnb ESLint rules (already configured)
- Always include `.js` file extensions in imports
- Use Unix line endings (LF)
- ESLint is the JS formatter (`npm run lint:fix`); never run Prettier on JS/MJS

### CSS
- HTML-first blocks: style only with Tailwind classes in the Block Source; never edit the generated `{blockname}.css`
- Responsive design is mobile first with the Tailwind default breakpoints: `sm` 640px, `md` 768px, `lg` 1024px, `xl` 1280px, `2xl` 1536px
- Hand-written CSS (Legacy Blocks, `styles/`):
  - Follow Stylelint standard configuration
  - Use modern CSS features (CSS Grid, Flexbox, CSS Custom Properties)
  - Use `min-width` media queries at the same breakpoints as Tailwind (640/768/1024/1280px)
  - Ensure all selectors are scoped to the block.
    - Bad: `.item-list`
    - Good: `.{blockname} .item-list`
  - Avoid classes `{blockname}-container` and `{blockname}-wrapper` as those are used on sections and could be confusing.
- Global CSS is intentionally minimal (reset + font): there is no global typography, button, link or section layout styling
- {{FONT_FAMILY}} is the main font: use `var(--font-family)` / `font-sans` (or inherit it) instead of declaring other font families

### HTML
- Use semantic HTML5 elements
- Author-facing text (UE labels, default copy, Drafts) is in {{LANGUAGE_NAME}}
- Ensure accessibility standards (ARIA labels, proper heading hierarchy)
- Follow AEM markup conventions for blocks and sections

## Key Concepts

### Content

CMS authored content is a key part of every AEM Website. The content of a page is broken into sections. Sections can have default content (text, headings, links, etc.) as well as content in blocks.

If no authored content exists to test against, use the static HTML files in the `drafts/` folder at the project root (`npm run aem:up` already passes `--html-folder drafts`). HTML-first blocks get `drafts/{blockname}.html` automatically; for other pages follow the aem markup structure and save files with `.html` or `.plain.html` extensions.

Background on content and markup structure can be found at https://www.aem.live/developer/markup-sections-blocks and https://www.aem.live/developer/markup-reference respectively.

You can inspect the contents of any page with `curl http://localhost:3000/path/to/page`, `curl http://localhost:3000/path/to/page.md`, and `curl http://localhost:3000/path/to/page.plain.html`

### Content Modeling

Modeling the content for blocks and sections must follow the best practices on https://www.aem.live/developer/component-model-definitions

For HTML-first blocks the model is derived from the Block Source: never edit `_{blockname}.json`, run `npm run aem:build` instead (it also registers the block in the `section` filter). For Legacy Blocks and `models/`, after changing a partial file (`_{blockname}.json` for example) run `npm run build:json` to regenerate the aggregated definitions, models and filters.

Use `npm run lint` to verify the models follow the best practices. You can refer to https://github.com/adobe-rnd/eslint-plugin-xwalk?tab=readme-ov-file#rules for more details about the applied rules.

Remember, building semantically appealing block, section and document models is key to  built websites with Edge Delivery Services in Adobe Experience Manager Sites as a Cloud Service using Universal Editor.

You can find plenty of examples, also for complex use cases, on GitHub https://github.com/adobe-rnd/aem-boilerplate-xwalk/pulls?q=is%3Aopen+is%3Apr+label%3AExample

### Blocks

Blocks are the re-usable building blocks of AEM. Blocks add styling and functionality to content. Each block has an initial content structure it expects, and transforms the html in the block using DOM APIs to render a final structure. 

The initial content structure is important because it impacts how the author will create the content and how you will write your code to decorate it. In some sense, you can think of this structure as the contract for your block between the author and the developer. You should decide on this initial structure before writing any code, and be careful when making changes to code that makes assumptions about that structure as it could break existing pages.

For HTML-first blocks this contract is the Block Source (see "HTML-first blocks" above): the generated `{blockname}.js` renders it and any extra behaviour goes in `{blockname}.enhance.js`. The rest of this section applies to Legacy Blocks.

The block javascript should export a default function which is called to perform the block decoration:

```
/**
 * loads and decorates the block
 * @param {Element} block The block element
 */
export default async function decorate(block) {
  // 1. Load dependencies
  // 2. Extract configuration, if applicable
  // 3. Transform DOM
  // 4. Add event listeners
}
```

Use `curl` and `console.log` to inspect the HTML delivered by the backend and the DOM nodes to be decorated before making assumptions. Remember that authors may omit or add fields to a block, so your code must handle this gracefully.

Each block should be self-contained and re-useable, with CSS and JS files following the naming convention: `blockname.css`, `blockname.js`. Blocks should be responsive and accessible by default.

### Three-Phase Page Loading

Pages are progressively loaded in three phases to maximize performance. This process begins when `loadPage` from scripts.js is called.

* Eager - load only what is required to get to LCP. This generally includes decorating the overall page content to create sections, blocks, buttons, etc. and loading the first section of the page.
* Lazy - load all other page content, including the header and footer.
* Delayed - load things that can be safely loaded later here and incur a performance penalty when loaded earlier

## Deployment

### Environments

Your local development server at `http://localhost:3000` serves code from your local working copy (even uncommitted code) and content that has been previewed by authors. You can access this at any time when the development server is running.

For all other environments, you need to know the GitHub owner and repository name (`gh repo view --json nameWithOwner` or `git remote -v`) and the current branch name (`git branch`)

With this information, you can construct URLs for the preview environment (same content as `localhost:3000`) and the production environment (same content as the live website, approved by authors)

- **Production Preview**: `https://main--{repo}--{owner}.aem.page/`
- **Production Live**: `https://main--{repo}--{owner}.aem.live/`
- **Feature Preview**: `https://{branch}--{repo}--{owner}.aem.page/`

### Publishing Process
1. Push changes to a feature branch
2. AEM Code Sync automatically processes changes making them available on feature preview environment for that branch
3. Run a PageSpeed Insights check at https://developers.google.com/speed/pagespeed/insights/?url=YOUR_URL against the feature preview URL and fix any issues. Target a score of 100
4. Open a pull request to merge changes to `main`
   1. in the PR description, include a link to `https://{branch}--{repo}--{owner}.aem.page/{path}` with a path to a file that illustrates the change you've made. This is the same path you have been testing with locally. WITHOUT THIS YOUR PR WILL BE REJECTED
   2. If an existing page to demonstrate your changes doesn't exist, create test content as a static html file and ask the user for help copying it to a cms content page you can link in the PR
5. use `gh pr checks` to verify the status of code synchronization, linting, and performance tests
6. A human reviewer will review the code, inspect the provided URL and merge the PR
7. AEM Code Sync updates the main branch for production
